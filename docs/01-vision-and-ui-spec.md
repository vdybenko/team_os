# TeamOS — Vision & UI Specification

> Версія 0.2 · 2026-11-21 · Статус: рішення по відкритих питаннях прийняті, йде прототип
> Наступні кроки: (1) клікабельний HTML-прототип за цим документом → (2) архітектура → (3) MVP

---

## 1. Проблема

Команда домовляється про речі **в розмовах** — на мітингах, у чатах, у листах. А фіксувати це потрібно **в інструментах** — Notion, Confluence, Jira, Linear. Між ними прірва:

- Після мітингу кожен пам'ятає своє: «я думав, дедлайн п'ятниця», «я не знав, що це на мені».
- Записувати домовленості вручну — довго, і ніхто цього не робить системно.
- Знання розкидане: частина в транскрипті, частина в чаті, частина в голові. Онбординг нової людини = годинні розповіді «як у нас заведено».
- Таск-трекери заточені під розробку, а не під **комітменти між людьми** («ти обіцяв мені X до четверга»).

**Інсайт:** 80% інформації вже існує в цифровому вигляді (транскрипти, листи, календар, документи). Не треба змушувати людей писати — треба **витягувати, пропонувати і давати підтвердити**.

## 2. Vision

**TeamOS — це «другий мозок» команди, який сам наповнюється з ваших розмов.**
Ви кидаєте в нього все, що відбулося (транскрипт, лист, кусок чату, документ). Він витягує комітменти, зміни статусів і знання, а ви лише підтверджуєте одним кліком. У результаті в команди є одне джерело правди: хто кому що винен, що ми вирішили і чому, над якими гіпотезами працюємо.

**Принципи продукту**

1. **Capture without writing.** Головний ввід — не форма, а «кинь сюди».
2. **Human-in-the-loop.** AI нічого не записує в спільний простір без підтвердження людини. AI пропонує — людина вирішує.
3. **Кожен факт має джерело.** Будь-яка задача чи рішення посилається на цитату з транскрипту/листа, звідки воно взялось.
4. **Комітмент ≠ таска.** У центрі — зобов'язання між людьми (хто → кому → що → до коли), а не тікет.
5. **Приватне за замовчуванням.** Сирі джерела (транскрипт, лист) бачить тільки той, хто їх додав. Команді потрапляє лише підтверджене.
6. **Open-source first.** Той самий код — SaaS для нас і для інших, або self-host у себе, щоб дані не покидали компанію.

**Для кого (ICP v1)**
- Маленькі команди 3–20 людей, що формуються: стартапи, агенції, продуктові команди, ініціативні групи.
- Лідер команди / фаундер, який проводить багато мітингів і тримає в голові всі домовленості.
- Тімлід, що робить 1:1 і хоче бачити «що ми обіцяли один одному».
- Також: особисте використання (personal workspace) — свій другий мозок.

**Чого ми свідомо НЕ робимо в v1**
- Не замінюємо Jira для розробки зі спринтами, story points, епіками.
- Не робимо власний записувач мітингів (беремо готові транскрипти з Meet/Zoom/Omi/Fireflies тощо).
- Не робимо месенджер.

## 3. Основний цикл (core loop)

```
  ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌────────────┐    ┌──────────┐
  │ CAPTURE │ →  │ EXTRACT  │ →  │  REVIEW  │ →  │   STORE    │ →  │   USE    │
  │ Inbox   │    │ LLM      │    │ Proposals│    │ Tasks,     │    │ Dashboard│
  │         │    │ analysis │    │ approve/ │    │ Knowledge, │    │ 1:1 view │
  │transcr. │    │          │    │ edit/    │    │ Projects,  │    │ Ask      │
  │mail,doc │    │          │    │ reject   │    │ Hypotheses │    │ Onboard  │
  └─────────┘    └──────────┘    └──────────┘    └────────────┘    └──────────┘
        ↑                                                                │
        └──────── наступний мітинг закриває/оновлює комітменти ──────────┘
```

Ключове: петля замикається. Наступний транскрипт не лише створює нові задачі, а й **пропонує оновити статуси старих** («Сашко сказав, що задеплоїв → закрити задачу?»).

## 4. Доменна модель (сутності)

| Сутність | Суть | Ключові поля |
|---|---|---|
| **User** | Людина, логін через Google | name, email(s), avatar, aliases (як її називають у транскриптах: «Вова», «Volodymyr») |
| **Workspace (Team)** | Команда. У кожного юзера автоматично є Personal workspace | name, owner, members, inbox-email |
| **Membership** | Роль юзера в команді | role: Owner / Admin / Member, joined_at, status (invited/active) |
| **Connected account** | Підключений Google-акаунт (робочий/особистий), можна кілька | email, services: Calendar ☐ Gmail ☐ Drive ☐, вибрані календарі |
| **Inbox item** | Будь-яке вхідне джерело | type (transcript / email / doc / chat / calendar event / note), raw content, uploader, team context, linked calendar event, status |
| **Proposal** | Пропозиція, яку AI витяг з inbox item | kind (new commitment / status change / knowledge / new project / new hypothesis), payload, confidence, evidence (цитата + позиція в джерелі), state (pending / approved / edited / rejected) |
| **Commitment (Task)** | Зобов'язання | title, description, **owner** (хто має зробити), **requester** (хто поставив / кому зобов'язались; може бути зовнішня людина), creator, deadline, priority (urgent ☐ important ☐), status, project, hypothesis, source evidence, comments, history. Окремого поля visibility немає: задачу бачать тільки її учасники (+ Owner/Admin команди) |
| **Knowledge item** | Домовленість/рішення/факт | type (decision / agreement / fact / process / context), text, rationale, scope (private / team), project, tags, source evidence, valid_from, supersedes → |
| **Project** | Продукт/напрям/проєкт | name, vision, goal(s), owner, status, members |
| **Hypothesis** | Що зараз тестуємо всередині проєкту | statement («Якщо… то… бо…»), owner, success metric, timeframe, status (draft / testing / validated / invalidated), learnings |
| **Comment** | Коментар до задачі/гіпотези/знання | author, text, created_at |
| **External contact** | Людина поза командою (клієнт, партнер) | name, email — для комітментів «я обіцяв клієнту» |

**Напрям комітменту** (головна вісь для UI):
- **Я винен** — owner = я
- **Мені винні** — requester = я, owner = інший (= делеговане)
- **Командне** — між іншими членами команди (видно тільки Owner/Admin)
- **Зовнішнє** — я винен зовнішньому контакту або він мені

**Статуси комітменту:** `Open → In progress → Waiting/Blocked → Done | Cancelled`
Статус змінює **тільки той, хто поставив задачу** (requester). Виконавець пише коментар («зроблено, ось лінк»), а AI може запропонувати зміну статусу з транскрипту — і те, і інше requester бачить і підтверджує сам.

## 5. Ролі та права

### 5.1 Ролі в команді

| Дія | Owner | Admin | Member |
|---|:-:|:-:|:-:|
| Перейменувати / видалити команду, білінг | ✅ | — | — |
| Передати ownership | ✅ | — | — |
| Запрошувати / видаляти учасників | ✅ | ✅ | — |
| Змінювати ролі (крім Owner) | ✅ | ✅ | — |
| Створювати / редагувати проєкти, vision, гіпотези | ✅ | ✅ | 🟡 тільки свої гіпотези |
| Бачити всі командні комітменти (між іншими людьми) | ✅ | ✅ | ❌ лише ті, де він виконавець або постановник |
| Бачити free/busy календарів команди | ✅ | ✅ | ✅ (якщо людина дозволила) |
| Додавати в Inbox і створювати свої задачі | ✅ | ✅ | ✅ |
| Зберігати knowledge на рівні команди | ✅ | ✅ | ✅ (з позначкою автора) |

### 5.2 Права на конкретний комітмент

| Дія | Requester (поставив) | Owner (виконує) | Admin/Owner команди | Інші members |
|---|:-:|:-:|:-:|:-:|
| Бачити | ✅ | ✅ | ✅ | ❌ |
| Коментувати | ✅ | ✅ | ✅ | ❌ |
| Редагувати назву/дедлайн/проєкт/пріоритет | ✅ | ❌ | ❌ | ❌ |
| Змінювати статус (будь-який, включно з Done/Cancelled) | ✅ | ❌ | ❌ | ❌ |
| Перепризначити | ✅ | ❌ | ❌ | ❌ |
| Передати роль requester-а (edge case: людина пішла з команди) | — | — | ✅ | ❌ |

**Правило:** статус і поля задачі змінює **тільки той, хто її поставив**. Виконавець — лише коментує. Самопоставлена задача (я = requester = owner) — повністю моя.
Пропозиції AI про зміну статусу завжди йдуть requester-у: якщо транскрипт додав інший учасник, пропозиція по чужій задачі переадресовується в Inbox requester-а.

### 5.3 Приватність джерел
- **Inbox тільки особистий.** Кожен має свій інбокс; item прив'язується до команди як контекст для аналізу.
- Сирий inbox item (транскрипт, лист) бачить **тільки той, хто його додав**.
- Учасники команди бачать **підтверджені** задачі/знання з цитатою-доказом (1–3 речення), але не весь транскрипт.
- Календар: команда бачить тільки **free/busy** за замовчуванням; деталі подій — тільки якщо людина ввімкнула.
- Пошта: ніколи не шериться з командою автоматично; лише те, що людина сама відправила в Inbox.

## 6. Інформаційна архітектура (ліве меню)

```
┌──────────────────────────┐
│ [▼ Linxa Team]           │  ← перемикач команд (+ Personal, + Create team)
│ ⌘K  Search / Ask         │
├──────────────────────────┤
│ 🏠 Dashboard             │
│ 📥 Inbox            (3)  │  ← бейдж = пропозиції, що чекають на review
│ ✅ Tasks                 │
│ 📅 Calendar              │
│ ✉️  Mail             (5) │  ← листи, що потребують реакції
│ 🧠 Knowledge             │
├──────────────────────────┤
│ TEAM SPACE               │
│ ◆ Team vision            │
│ ▸ Linxa                  │  ← проєкти; розкриваються в гіпотези
│ ▸ TeamOS                 │
│ + New project            │
├──────────────────────────┤
│ 👥 Members               │
│ 🔌 Connections           │
│ ⚙️  Settings             │
│ [avatar] Volodymyr       │
└──────────────────────────┘
```

Глобальні елементи:
- **«+ Add to Inbox»** — головна кнопка, доступна з будь-якого екрану (і хоткей `I`).
- **⌘K** — пошук + «Ask TeamOS» (питання природньою мовою до бази знань, відповідь з посиланнями на джерела).
- **Task drawer** — будь-яка задача відкривається боковою панеллю справа, не новою сторінкою.


## 7. Екрани

### 7.1 Login
- Один екран: лого, слоган «Your team's second brain — built from your meetings», кнопка **Continue with Google**.
- Під кнопкою: «Open-source · Self-host available» + посилання на GitHub.
- Якщо людина прийшла за інвайт-лінком — над кнопкою картка: «Volodymyr запросив тебе в команду **Linxa Team**».

### 7.2 Onboarding (перший вхід)
Степер з 3 кроків, кожен можна пропустити:

1. **Команда.** «Create a team» (назва) або «Join» (якщо є інвайти) або «Use personally».
2. **Запроси людей.** Поле email-ів + роль (Member/Admin), «Skip for now».
3. **Підключи джерела.** Картки Google Calendar / Gmail / Google Drive з кнопкою Connect. Після підключення — можна «+ Add another Google account».
4. **Перший вау-момент.** «Кинь сюди транскрипт останнього мітингу» (або «Try with sample transcript»). → одразу відкривається Review (7.5).

**Для запрошеного учасника** онбординг коротший: прийняти інвайт → підключити календар (з поясненням «команда бачитиме лише free/busy») → Dashboard з порожніми станами («Тут з'являться задачі, які тобі делегують»).

### 7.3 Dashboard
Сітка з віджетів. Зверху — привітання і рядок «стан дня»: `3 пропозиції чекають review · 2 прострочені комітменти · 4 мітинги сьогодні`.

| Віджет | Зміст |
|---|---|
| **Мої комітменти** | Список «Я винен», сортування по дедлайну; червоні — прострочені, жовті — сьогодні/завтра. Чекбокс швидкої зміни статусу. Таби: `Всі / Команді / Зовнішнім` |
| **Делеговане (мені винні)** | Згруповано по людях: аватар + к-сть + найближчий дедлайн. Клік → Person view (7.8) |
| **Календар сьогодні** | Таймлайн дня. Перемикач: `Мої календарі ▾` (чекбокси календарів) / `Команда` (free/busy смуги учасників). На кожному мітингу дві кнопки: **Prep** (агенда з відкритих комітментів між учасниками) і **Drop transcript** (після завершення) |
| **Inbox** | «3 items need review» + останні оброблені |
| **Нещодавні рішення** | Останні 5 knowledge items рівня команди |
| **Активні гіпотези** | Гіпотези в статусі testing: назва, owner, дні до кінця таймфрейму, прогрес задач |

### 7.4 Inbox — список
Таби: **Needs review (3)** · **Processing (1)** · **Done** · **Ignored**

Кожен рядок:
`[іконка типу] Назва (напр. «Weekly sync — 20 Nov») · джерело · team · дата · результат: 5 tasks · 2 updates · 7 knowledge · [Review →]`

Статуси item: `Queued → Processing → Needs review → Partially applied → Done` (+ `Failed`, `Ignored`).

**Модалка «Add to Inbox»** (кнопка зверху):
- Табs: **Paste text** (транскрипт, кусок чату) · **Upload file** (txt, md, docx, pdf, vtt, srt) · **From Drive** (picker) · **From Gmail** (вибрати лист) · **Note** (надиктувати/написати думку)
- Поля: Team context (авто-визначений, можна змінити), «Пов'язати з мітингом» (дропдаун останніх подій календаря — дає учасників і дату → кращий матчинг людей), назва.
- Підказка внизу: «Або пересилай листи на `linxa-team.k7f2@in.teamos.app`».

### 7.5 Inbox — Review (ключовий екран продукту)
Дві колонки:

**Ліва (40%) — Джерело.** Транскрипт/лист з підсвіченими фрагментами. Наведення на пропозицію праворуч → скрол і підсвітка цитати зліва. Зверху: мітинг, учасники (замаплені на членів команди; незамаплених можна прив'язати: «"Сашко" → Oleksandr S.»).

**Права (60%) — Пропозиції**, згруповані в секції з лічильниками. Кожна картка має чекбокс (за замовчуванням ✅ якщо confidence високий), бейдж впевненості і цитату-доказ.

1. **Нові комітменти (5)**
   Картка: `☑ Підготувати pricing page для MCP`
   `Owner: [Oleksandr ▾] → Requester: [Volodymyr ▾] · Deadline: [Пт, 28 Nov ▾] · Project: [Linxa ▾] · Hypothesis: [MCP freemium ▾] · Priority: [Important ▾]`
   `“…Саш, давай ти до п'ятниці зробиш сторінку з цінами…” 12:41`
   Поля редагуються інлайн. Якщо AI вагається — показує альтернативу: «Можливо, проєкт TeamOS?».

2. **Оновлення статусів (2)**
   `☑ «Задеплоїти webhook-и Pipedrive» · In progress → **Done**`
   `“…вебхуки вже на проді з вівторка…” 08:15`
   Якщо задачу поставив не я — пропозиція не застосовується, а **відправляється requester-у** на підтвердження (позначка «→ піде на підтвердження Volodymyr»).

3. **Знання (7)**
   `☑ [Decision] Безкоштовний тариф MCP — 100 викликів/міс.` · Scope: `[🔒 Тільки я | 👥 Команда]` · Project: Linxa
   Якщо суперечить існуючому: ⚠️ «Суперечить рішенню від 12 Nov: "50 викликів/міс". [Замінити старе] [Зберегти обидва]».

4. **Інше (1)** — пропозиції нових проєктів/гіпотез, нових людей/зовнішніх контактів.

**Нижня панель (sticky):** `Selected: 12 of 15 · [Reject unselected & apply] · [Save draft]`. Хоткеї: `J/K` — навігація, `Space` — чекбокс, `E` — редагувати, `⌘Enter` — застосувати.

**Мета UX:** розібрати годинний мітинг за < 3 хвилини.

### 7.6 Tasks
Хедер: перемикач представлень + фільтри (`Direction: Я винен / Мені винні / Команда`, `Person`, `Project`, `Hypothesis`, `Status`, `Deadline`) + «+ New task» (ручне створення теж є).

**a) Eisenhower Matrix** — 4 квадранти:
`Do now (Urgent+Important)` · `Schedule (Important)` · `Delegate (Urgent)` · `Drop (–)`.
Urgency рахується автоматично з дедлайну (≤ 2 дні = urgent, налаштовується), importance — прапорець. Drag між квадрантами змінює прапорці. У квадранті «Delegate» — кнопка «Делегувати» на кожній картці.

**b) Kanban** — колонки за статусами: `Open · In progress · Waiting/Blocked · Done`. Swimlanes опційно по людях або проєктах. Drag дозволений лише там, де є права (інакше картка «пружинить» і з'являється тултіп «Тільки Volodymyr може закрити»).

**c) List** — таблиця: назва · owner · requester · deadline · status · project · hypothesis · source. Групування: по людині / проєкту / дедлайну.

**d) Delegated** — пресет: тільки «мені винні», групування по делегатах, лічильники «відкрито / прострочено / є нові коментарі». Це основа для 1:1.

**Task drawer** (відкривається справа з будь-якого місця):
- Назва, статус, owner → requester, дедлайн, пріоритет, проєкт, гіпотеза.
- **Source**: цитата + посилання на inbox item («з Weekly sync 20 Nov, 12:41»).
- **Activity**: історія змін (хто, коли, з якого джерела — «статус змінено на Done з транскрипту 27 Nov, підтвердив Volodymyr»).
- **Comments**.
- Для виконавця: поля read-only, плашка «Статус змінює Volodymyr — напиши коментар, якщо є оновлення». Доступні лише коментарі.

### 7.7 Calendar
- Вид тиждень/день. Ліворуч — список календарів з усіх підключених акаунтів (чекбокси, кольори).
- Секція **Team availability**: чекбокси членів команди → їхні free/busy як сірі блоки поруч.
- Клік по події → панель: учасники (хто в команді), **Prep** — відкриті комітменти між учасниками + рішення по пов'язаних проєктах з минулих мітингів, та **Drop transcript** / «Транскрипт знайдено в Drive → Обробити».
- Події з дедлайнами задач показуються як маленькі маркери на день.

### 7.8 Person view (1:1 / Meeting mode)
Відкривається кліком по людині (Dashboard, Members, Tasks-фільтр).
- Хедер: аватар, роль, найближчий спільний мітинг.
- Дві колонки: **Я винен їй/йому** · **Вона/він винен мені**.
- Режим **Meeting mode**: великі картки по одній, з кнопками статусу (`✅ Done · ▶ In progress · ⏸ Blocked · 📅 Перенести дедлайн · 💬 Коментар`). Ідеально для «пройтись по статусах» на 1:1.
- Внизу: спільні рішення/знання за останній місяць.

### 7.9 Mail
- Об'єднаний список з усіх підключених Gmail-акаунтів, але **тільки важливе**, AI-тріаж по категоріях:
  `Потребує відповіді` · `Чекаю відповіді (я написав, мені не відповіли)` · `Містить комітмент` · `FYI`.
- Кожен рядок: від кого, тема, 1 рядок суті від AI, з якого акаунта (кольорова мітка), кнопка **→ Inbox** (відправити на аналіз) і **Open in Gmail**.
- Фільтр по акаунтах.
- TeamOS не є поштовим клієнтом: відповідь — через Gmail.

### 7.10 Knowledge
- Стрічка/таблиця knowledge items з фільтрами: тип (Decision / Agreement / Fact / Process / Context), scope (Мої / Командні), проєкт, автор, період.
- Кожен item: текст, rationale («чому»), джерело, дата, автор підтвердження, «замінює → / замінено ←».
- **Decision log** — пресет: тільки рішення в хронології, з видимою історією заміни.
- Ручне додавання/редагування теж можливе.
- Кнопка **Onboarding pack** (P1): AI збирає з командних знань і Team Space документ «що треба знати новенькому» → посилання для нового учасника.

### 7.11 Team Space
**Team vision** — сторінка-документ: місія, цінності, як ми працюємо (rich-text редактор, редагують Owner/Admin).

**Project page** — таби:
- **Overview**: vision проєкту, цілі (goal + метрика + target + дата), owner, учасники, прогрес (відкриті/закриті задачі).
- **Hypotheses**: картки-гіпотези — `Якщо [дія], то [результат], бо [припущення]` · owner · метрика успіху · таймфрейм · статус (Draft / Testing / Validated / Invalidated) · прогрес задач. Клік → Hypothesis page.
- **Tasks**: усі задачі проєкту (той самий компонент Tasks із пресетом-фільтром).
- **Knowledge**: рішення та домовленості по проєкту.

**Hypothesis page**: формулювання, owner, метрика і поточне значення (вручну), статус, прив'язані задачі, **Learnings** (висновки; AI пропонує їх з транскриптів: «на мітингу сказали, що конверсія 2% → додати як learning?»), фінальний вердикт.

Ієрархія: `Team → Project → Hypothesis → Task`. Задача може бути без проєкту; гіпотеза завжди в проєкті.

### 7.12 Members
- Таблиця: людина, email, роль (дропдаун), статус (Active / Invited · resend), календар доступний для free/busy ☐, к-сть відкритих комітментів.
- «Invite» — модалка: email-и + роль.
- Дії: змінити роль, видалити, **Transfer ownership** (тільки Owner, з підтвердженням вводом назви команди).

### 7.13 Connections
- Картки підключених Google-акаунтів: `vd@linxa.com` · `volodymyr@gmail.com`. На кожній — перемикачі сервісів: Calendar (+ вибір конкретних календарів), Gmail, Drive. Статус синхронізації, «Disconnect».
- «+ Connect another Google account».
- Інші джерела (P2): Telegram bot, Slack, Zoom, Omi, Fireflies, Webhook/API, MCP.

### 7.14 Settings
- **Team**: назва, inbox-email адреса, мова аналізу, правило urgency (днів до дедлайну).
- **Privacy**: що команда бачить з мого календаря (free/busy / деталі / нічого), чи шерити сирі джерела за замовчуванням.
- **AI**: (для self-host) провайдер і ключ — OpenAI / Anthropic / Gemini / локальна модель; автоприйняття пропозицій з високим confidence (вимкнено за замовчуванням).
- **Notifications**: щоденний дайджест (email/Telegram): нові делеговані задачі, прострочене, що чекає review.

## 8. Ключові user flows

**Flow A — Після мітингу (головний)**
Мітинг закінчився → на Dashboard у події з'являється «Drop transcript» (або TeamOS сам знайшов транскрипт у Drive) → вставляю → 20–40 с обробки → Review → правлю 2 поля, знімаю 3 галочки → Apply → у членів команди з'являються задачі + сповіщення.

**Flow B — Делегування і контроль**
Я в Review ставлю Owner = Oleksandr → у нього в Dashboard «Мені поставили: 1» → він пише коментар «готово, ось лінк» → я бачу непрочитаний коментар на Dashboard → сам змінюю статус. Або на наступному 1:1 відкриваю Person view → Meeting mode → проходжу статуси.

**Flow C — Наступний мітинг закриває старі задачі**
Кидаю новий транскрипт → у секції «Оновлення статусів» AI знайшов 3 відкриті задачі, про які говорили → підтверджую зміни.

**Flow D — Запрошення в команду**
Owner → Members → Invite (email, роль) → лист з лінком → людина логіниться Google-акаунтом (будь-яким; email інвайта і акаунта можуть відрізнятись — інвайт прив'язується за лінком) → коротке онбординг → бачить порожній Dashboard з поясненням.

**Flow E — Новий учасник онбордиться**
Admin генерує Onboarding pack → новий учасник читає vision, проєкти, активні гіпотези, ключові рішення з посиланнями на джерела → ставить питання в ⌘K Ask.

## 9. AI-аналізатор: що він робить

На вхід: inbox item + контекст команди (учасники та їхні aliases, проєкти, активні гіпотези, відкриті задачі, останні рішення).
На вихід (структурований JSON):
1. **Commitments**: хто → кому → що → дедлайн (нормалізований у дату з урахуванням дати мітингу: «до п'ятниці» → 28 Nov) → проєкт/гіпотеза (з поясненням вибору) → пріоритет.
2. **Status updates**: матчинг сказаного з існуючими відкритими задачами.
3. **Knowledge**: рішення / домовленості / факти + детекція конфліктів з існуючими.
4. **Entities**: нові люди, зовнішні контакти, кандидати в проєкти/гіпотези.
5. **Summary** мітингу (3–5 пунктів) — зберігається з inbox item.

Кожен пункт: `confidence` + `evidence` (цитата і позиція). Без evidence — пропозиція не показується.

Дедуплікація: якщо два учасники кинули транскрипт того самого мітингу (матч по події календаря / схожості) — показуємо «Цей мітинг вже обробив Oleksandr» і пропонуємо лише нове.

## 10. Етапи (scope)

**MVP v0.1 — для нашої команди (2–3 тижні)**
- Google login, workspaces (team + personal), ролі, інвайти, transfer ownership

- AI-аналіз → Review (commitments, status updates, knowledge) з evidence

- Google Calendar (кілька акаунтів)

**v0.2**
- Gmail (кілька акаунтів) + Mail triage + «→ Inbox»
- Drive picker + авто-підхоплення Meet-транскриптів

## 11. Метрики успіху

| Метрика | Ціль MVP |
|---|---|
| Час розбору 1-год мітингу в Review | < 3 хв |
| % пропозицій, прийнятих без редагування (precision) | > 70% |
| % реальних комітментів з мітингу, які AI знайшов (recall, ручна перевірка) | > 85% |
| Транскриптів на команду на тиждень | ≥ 3 |
| % делегованих задач, закритих через TeamOS (а не «загублених») | > 60% |
| Weekly active members / всі члени команди | > 70% |

## 12. Ризики та нотатки для архітектури

- **Google OAuth scopes.** Gmail (read) і повний доступ до Drive — це «restricted» scopes: для публічного SaaS потрібна верифікація Google з security assessment; Calendar — «sensitive» (простіша верифікація). Для нашої команди можна працювати в режимі testing (до 100 тестових юзерів) без верифікації. Для Drive в MVP краще `drive.file` через Picker. Деталі перевіримо на етапі архітектури.
- **Self-host:** кожен, хто розгортає, створює свій Google OAuth client — потрібна гарна інструкція.
- **Якість матчингу людей** (aliases, українські зменшувальні імена) — критично для довіри; потрібен зручний UI «прив'язати ім'я».
- **Довіра до AI**: жодного автозапису без підтвердження в v1; evidence обов'язковий.
- **Мова:** транскрипти змішані (UA/EN/RU) — аналізатор має бути мультимовним, UI — EN + UA.

## 13. Прийняті рішення (21 Nov 2026)

1. **Видимість задач:** Member бачить тільки задачі, де він виконавець або постановник. Чужих задач не бачить. Owner/Admin команди бачать усі.
2. **Сирі джерела** бачить тільки той, хто їх додав. Команда бачить лише підтверджені пункти з цитатою.
3. **Статус змінює тільки той, хто поставив задачу.** Виконавець лише коментує.
4. **Inbox тільки особистий.**
5. Розділ називається **Team Space**.
